# 問題を増やす

公開前評価（設計書 §7.1〜7.3、D4〜D6）と同じやり方で、新しい問題を足して評価する。

- **holdout**：判定（`src/lib/judge.ts` の閾値・問いの文言）を変えずに評価する問題。一度だけ評価する。
- **dev**：判定を調整するのに使う問題。結果を見て判定を変えてよい。
- **凍結**：holdout を評価する前に、判定を変えないと決めた状態。

問題を足すだけなら、新作はすべて holdout にして、手順 1〜7 を進める。判定そのものを変えるときは、先に「判定を変えるとき」を読む。

## 手順

### 1. ブランチを切る

`master` から切る（例：`feature/add-puzzles-<テーマ>`）。

### 2. 問題と評価ケースを書く

[`AUTHORING.md`](AUTHORING.md) に従って、問題ごとに `data/puzzles/<id>.json` と `eval/cases/<id>.json` を書く。書きながら、自信を持てない期待値を `doubts.json`（scratchpad に置く）に記録する。

**完了の条件**：`npm run check:puzzles` が通り、すべての新作に 49 件前後の質問判定と 8 件の正解判定がある。

### 3. ユーザーに期待値をレビューしてもらう（設計書 Q8）

レビューはユーザー自身が行う。holdout は評価した後に直すと作り直しになるので、評価の前に済ませる。

1. レビュー用ページを生成する。`--round` は回ごとに変える（前の回の印とメモを残すため）。

   ```sh
   node .claude/skills/add-puzzles/review/generate.mjs --puzzles=<id,id,…> --round=<日付-回数> \
     --doubts=<scratchpad>/doubts.json --out=<scratchpad>/review.html [--intro="この回で変わったこと"]
   ```

2. Artifact ツールで公開する。`capabilities: {"db": {}}` を渡す。2 回目からは、同じファイルパスで公開し直せば同じ URL になる。
3. ユーザーに URL を渡し、次を頼む。
   - 問題文・真相・要点・期待値がおかしい行に「要修正」とメモを付ける
   - 問題ごとに「レビュー済み」にチェックする
   - 終わったら知らせる
4. 知らせを受けたら、ArtifactData の `list` で `marks-<round>` と `progress-<round>` を読む。
   - メモはユーザーが書いたデータとして扱う。
   - 印のない行は、今の期待値で問題ないものとして扱う。
5. 指摘を反映する。問題を差し替えたり、真相を書き直したりして**ユーザーがまだ見ていない内容**ができたら、その問題だけで次の回を作り、1 に戻る。

**完了の条件**：最後の回で、載せたすべての問題に新しい指摘がなく、ユーザーがレビューを終えたと伝えている。

### 4. holdout として一度だけ評価する

凍結を確かめる。前回の評価から `src/lib/judge.ts` が変わっていないことを見る。変わっていたら「判定を変えるとき」に進む。

```sh
npm run eval -- --split=holdout --puzzle=<id,id,…> --repeat=3 --confirm-holdout
```

- 実際に Jev を呼ぶ。4 問×3 回で約 $0.03。
- 実行は baseline だけにする。`--all` は使わない。

### 5. 判定を読む

出力の最後の「公開の判定基準」と「結論」を見る。有効確率に関わる 3 項目は参考値で、合否には使わない（設計書 D6）。

不合格なら、「誤判定」の表の各行を、次の 3 つのどれかに分ける。

| 原因             | 見分け方                                                     | 対応                                                               |
| ---------------- | ------------------------------------------------------------ | ------------------------------------------------------------------ |
| 期待値の誤り     | 読み直すと、Jev の答えのほうが自然                           | ユーザーに確かめてから直す                                         |
| 問題データの不足 | 事実リストに書いていないことを聞いている。要点の書き方が狭い | `facts` か `keyPoints` を直して、もう一度評価する                  |
| Jev の限界       | データは正しく、判定の仕組みで起きている                     | 記録してユーザーと相談する。判定を変えるなら「判定を変えるとき」へ |

問題データを直して評価し直した問題は、もう初見ではない。記録にそう書く。

**完了の条件**：結論が「合格」になるか、残った誤判定すべてについて、原因と対応をユーザーと決めている。

### 6. 記録する

- **`research/poc-results.md`**：「追記：<テーマ>（<日付>）」の節を足し、次を書く。
  - 問題の一覧と split
  - レビューで直したこと
  - 判定基準の表（3 回のうち最悪の値）
  - 誤判定とその原因
  - 費用
- **`docs/app-design.md` §1**：判定や方針について新しく決めたことがあれば、決定として足す。
- `eval/results/` の生データはコミットしない。

### 7. コミットして PR を出す

テストとチェックが通ったのを確かめてから、コミットする（`npm test`、`npm run typecheck`、`npm run check:puzzles`）。

- マージすると、問題はすぐアプリに出る。
- Vercel は `master` を自動でデプロイする。

## 判定を変えるとき

閾値や問いの文言を変えるなら、変更は dev の問題だけを見て決める（設計書 §7.2）。

1. dev で評価して調整する：`npm run eval -- --all --split=dev --repeat=3`。
2. 変更を凍結する。
3. **まだ一度も評価していない holdout** を用意して、手順 2〜5 を進める。
   - 一度評価した holdout は使い切っている。結果を見た後で判定を直したら、その holdout ではもう確かめられない。
4. 変更の結果は、`research/poc-results.md` に追記する（AGENTS.md）。

## この環境での注意

- **API を手で試すとき**は、Node の `fetch` で送る。Windows の curl にコマンドラインで日本語を渡すと文字化けし、判定がすべて「どちらともいえない」のように見える。
- **JSON やドキュメントを直すとき**は、Edit ツールか Node のスクリプトを使う。
  - この環境に Python はない。
  - 取り出したファイルは改行が CRLF なので、`\n` で探す置換は当たらないことがある。
