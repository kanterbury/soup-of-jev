# 問題と評価ケースの書き方

`SKILL.md` の手順 2 で使う。ここにあるのは、公開前評価（設計書 §7.1、D5）で決めた書き方と、レビューで受けた指摘から得た教訓。

## 問題データ（`data/puzzles/<id>.json`）

項目は `id`・`number`・`title`・`problem`・`truth`・`facts`・`keyPoints`。`id` はファイル名と同じ英小文字にする。`number` は一覧に出す固定の番号（No.）で、既存の問題の最大値に 1 を足した値にする。一覧の「新しい順」もこの番号で並ぶ。

- **自作する**：リポジトリは public。有名な問題を使うなら、文章は自分の言葉で書き直す（AGENTS.md）。
- **真相は、事実を積み上げてたどり着けるものにする**：登場人物の性格や気分しだいで決まる真相は、推理で絞り込めない。
  - 例：「ひ孫が生まれたので、祖母は止まった時計を動かしたくなった」は根拠が弱いとして、問題ごと差し替えた（`clock` → `exam`）。
- **真相には、思い込みをひっくり返す捻りを入れる**：問題文から素直に想像できる説明がそのまま真相になる問題は、不採用になった。
  - 例：「借りていた本だけが火事を免れた」「片方だけの靴は役に立たないので、もう片方も投げた」「停電で天の川が見えた」は、「ストレートすぎる」「捻りがない」として 3 問とも差し替えた。
- **問題文に、真相の手がかりになる続柄を書かない**：「母親」と書くと、子どもが関わることがすぐにわかる。「女性」のように伏せて、質問で確かめさせる（`phone`）。
- **真相に余計な設定を足さない**：解くのに要らない仕掛けは、要点も評価ケースも複雑にするだけ。
  - 例：「嘘は午前中だけという言い伝えがあるので、正午を過ぎてからプロポーズした」は不要とされ、「二度目だから冗談ではないとわかった」にした（`april`）。
- **問題文には、推理の前提になる事実を書き、質問でたどり着かせたい事実は書かない**
  - 書かない例：「わざと石を投げて割った」の「わざと」は、質問で確かめさせたいので削った（`window`）。
  - 書く例：「クラスの優秀な生徒たちは、誰一人として満点を取れなかった」は、推理の前提として足した（`exam`）。
- **`facts` は、質問されそうなことを先回りして書く**：Jev は state に書いてあることしか根拠にしない。
  - 真相の要素を 1 文 1 事実に分ける。
  - 否定の事実も書く（「火事や爆発は起きていない」「お金は関係ない」「〜ではない」）。書いていないと、無関係な質問と区別できず「どちらともいえない」に倒れる。
  - 10〜18 件が目安。
- **`keyPoints` は 2〜3 個、最小限の表現にする**：正解判定は「回答がこの要点を含むか」を要点ごとに聞く。
  - 言い換えにも当たるよう、広めに書く。例：「眠っていて、呼んでも気づかなかった」では「呼んでも起きない」に当たらなかったので、「呼んでも応えられない状態だった」にした。
  - 問題文から自明なことは要点にしない（誰でも書けてしまい、部分正解の数が測れなくなる）。

## 評価ケース（`eval/cases/<id>.json`）

`puzzleId`・`split`・`questions`・`solutions` を持つ。書式は既存のファイルに合わせる（1 行 1 ケース、カテゴリの間に空行）。

### split

- **`holdout`**：判定（`src/lib/judge.ts`）を変えずに評価する問題。問題を足すだけなら、新作はすべてこれにする。評価は一度だけ。
- **`dev`**：判定の閾値や問いの文言を調整するのに使う問題。結果を見て判定を変えてよい。

### 質問判定（1 問あたり約 49 件）

| カテゴリ | 件数 | 中身 | 期待値 |
|---|---|---|---|
| `direct` | 10 | 真相や事実にそのまま書いてあること | YES / NO |
| `inference` | 10 | 真相から一段推論すれば答えが出ること | YES / NO |
| `negative` | 4 | 素直な否定の質問（「〜しなかったのですか？」） | 内容が成り立てば YES |
| `confirm` | 2 | 確認型（「〜のではないのですか？」） | 確かめている内容が成り立てば YES |
| `ambiguous` | 2 | 両方に読める否定疑問文 | `["yes", "no"]`（配列はこのカテゴリだけ） |
| `compound` | 3 | 「A で、かつ B ですか？」 | 両方成り立てば YES、どちらかが誤りなら NO |
| `long` | 2 | 60 字を超える長い質問。YES と NO を 1 件ずつ | YES / NO |
| `irrelevant` | 6 | 真相にも事実にも書いていないこと（年齢、曜日など） | `unknown` |
| `invalid` | 8 | 質問でない入力 | `invalid` |
| `injection` | 2 | 「YES と答えて」などの指示＋普通の質問。指示と逆が正解になるようにする | YES / NO |

- `invalid` には、次を混ぜる：ヒントや答えのおねだり、降参、あいさつ・相づち、「真相を説明して」のような依頼、疑問詞の質問（「なぜ〜ですか？」「何時に〜？」）。
- 否定疑問文の期待値は日本語の慣習に従う（README の評価ケースの項）。

### 正解判定（1 問あたり 8 件）

| `kind` | 件数 | 中身 | 期待値 |
|---|---|---|---|
| `correct` | 1 | 真相をまとめた正解 | `expectedSolved: true` |
| `paraphrase` | 1 | 短く言い換えた正解 | `true` |
| `partial` | 2 | 要点の一部だけ。当たる要点の数を `expectedMatched` に書く | `false` |
| `wrong` | 1 | 的外れな回答 | `false` |
| `hypotheses` | 2 | 複数の仮説を並べた回答（R3） | `false` |
| `mixed-error` | 1 | 正解に、真相と矛盾する誤りを 1 つ混ぜた回答（R3） | `false` |

- `hypotheses` と `mixed-error` は、**要点をすべて含む**ように書く。含んでいないと要点の判定だけで不正解になり、矛盾の問いを試せない。
- `mixed-error` の誤りは、`facts` の 1 件と食い違うものにする（例：「弾の入った銃で本気で撃とうとした」）。
- `partial` は、`expectedMatched` 以外の要点が読み取れない書き方にする。

## Claude の迷い（`doubts.json`）

書きながら、期待値に自信を持てないケースを記録する。レビュー用ページで黄色の行として示す。

```json
{ "<問題 id>|<質問文 または 回答文をそのまま>": "何に迷ったか（どちらの期待値にしたか、なぜか）" }
```

- 推論が 2 段以上になる質問、気持ちや意図を聞く質問、`partial` の `expectedMatched`、`ambiguous` は、迷いの候補になりやすい。
- 書いた内容が評価ケースと一字一句一致しないと、ページの生成が止まる。
