## 2. 背景

### 2.1 作りたいもの

水平思考クイズ（いわゆる「ウミガメのスープ」）をひとりで遊べる Web アプリ。

- サーバーには問題文と、非公開の真相を用意しておく。
- プレイヤーが YES/NO で答えられる質問をすると、AI が「YES／NO／どちらともいえない」で答える。
- プレイヤーは質問を重ねて真相を推理し、最後に回答する。

### 2.2 判定に使うモデル：Jev

TypeSafe AI の Jev を判定に使う。詳細は `research/what-is-jev.md` にあり、この設計に効く性質は次のとおり。

- **テキストを生成しない**：スキーマで決めた型付きの値と確率だけを返す。そのため、選択肢以外の値は返らず、真相の文章が出力される経路もない。
- **3 種類の問い**を 1 リクエストで並列に評価できる。
  - Choice：選択肢から 1 つを選ぶ。確信度（confidence）も返る。
  - boolean：真である確率を返す。直接 API では Noul と呼ぶ。
  - Score：段階で採点する。
- **state 以外の知識を持たない**：渡された情報だけを根拠に判定する。
- **弱点**：質問を字義通りに読む。多段の推論が苦手。
- **速度と費用**：1 リクエスト約 230ms（p50）、約 $0.0004。

### 2.3 PoC の結果（要約）

詳細は `research/poc-results.md` にある。

- **結論**：Go（条件付き）。
- **評価の規模**：3 問（ウミガメのスープ、7階で降りる男、バーの銃）。質問判定 120 件と正解判定 12 件を、4 条件で 3 回実行した。すべて直接 API（`jev-latest`）で行った。
- **最新（3 回目）の baseline**
  - 全体の正答率は 97.5%、直接 100%、推論 93.3%。
  - 質問でない入力の検出とインジェクションは 100%。
  - 正解判定は 12/12。
- **確信度は信頼できる**：確信度 0.9 以上の判定は、4 条件とも 100% 正答だった。
- **事実リストは必須**：外すと、全体の正答率が 89.2% に下がる。
- **確信度は「入力が質問かどうか」を表さない**
  - 「答えを教えてください」のような入力にも、3 択の確信度は 0.93〜0.99 と高く出る。
  - そのため、入力を質問として扱うかは、有効確率（後述）だけで決める。
- **「条件付き」の条件**
  - 評価セットが小さい。
  - 評価セットの作成・分析・修正と、閾値 0.3 の決定を、同じデータで同じ作成者が行った（合わせ込みの可能性）。
  - この 2 つを、§7 の公開前評価で解消する。

## 3. スコープ

### 3.1 MVP に入れるもの

- 問題の一覧と、問題ごとの進行状況（未挑戦／挑戦中／正解済み／真相を確認済み）
- 質問と判定のやり取り（プレイ画面）
- 回答の提出と正解判定（不正解のときは、当たった要点の数を表示する）
- 「真相を見る」ボタンで、解かずに真相を見る
- Vercel Hobby への公開（§7.4）
- 問題への「いいね」と、一覧での集計数の表示（D8。MVP の公開後に追加）
- 問題一覧の並び替え（新しい順／いいねの多い順。D9。MVP の公開後に追加）
- 問題ごとに 3 つのヒントを、1 つずつ開けるようにする（D11。MVP の公開後に追加）

### 3.2 MVP に入れないもの

| 機能                                                 | 入れない理由                                                                                                                                                                                                                                                                                    |
| ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ログイン、DB、質問の記録                             | 1 人用で遊ぶだけなら不要。DB と質問の記録は、ログイン機能と一緒に導入する（Q5）。例外として、いいねの数だけは Upstash Redis に保存する（D8）。アクセス解析（GA4）には、質問文を含まないイベントだけを送る（D10）。そのときは、内部の判定（`irrelevant` / `uncertain` など）をそのまま記録に使う |
| 判定の誤りを報告するボタン                           | 保存先がないため（Q5）                                                                                                                                                                                                                                                                          |
| 複数人プレイ                                         | リアルタイム同期が必要で、規模が大きい                                                                                                                                                                                                                                                          |
| 問題の管理画面                                       | 問題数が少ないうちは、JSON を PR でレビューするほうが安全（評価ケースも同時にレビューできる）                                                                                                                                                                                                   |
| 「重要な質問」バッジ                                 | 判定用の問い（`importance`）を PoC で評価していない。問い自体も外した（D2）。出すときは、問いを足し直して評価する                                                                                                                                                                               |
| 確信度が低いときの LLM へのエスカレーション          | Jev だけで目標の精度が出ている。§7 の基準を満たさなかったときに再検討する                                                                                                                                                                                                                       |
| 有効確率を補う狭い問い（「答えを求める依頼か」など） | 閾値 0.3 のまま、公開前の評価で確かめる（Q4）                                                                                                                                                                                                                                                   |
| アプリ内での 1 日あたりのリクエスト数の上限          | 数える場所（DB など）がない。費用はレート制限と支出の上限で守る（Q9）                                                                                                                                                                                                                           |

### 3.3 前提

- 1 人用のみ、ログインなし。進行状況はブラウザ（localStorage）に置く。
- 問題は JSON ファイルで管理する。
- スタイリングは Tailwind CSS v4 を使う（ユーザー指定）。

## 4. 判定の仕組み

### 4.1 現在のコード（PoC 時点）

TypeScript、Next.js 16（App Router）、`ai` 7.x を使っている。

| パス                               | 役割                                                                                                                                                                                                                                                       |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/lib/jev/client.ts`            | Jev の呼び出し。`JevClient` インターフェースの裏で、直接 API（`DirectJevClient`）と Vercel AI Gateway（`GatewayJevClient`）を切り替える。今の `createJevClient()` は、`TYPESAFE_API_KEY` があれば直接 API、なければ `AI_GATEWAY_API_KEY` で Gateway を使う |
| `src/lib/judge.ts`                 | 判定ロジック。`judgeQuestion()`、`judgeSolution()`、`DEFAULT_JUDGE_OPTIONS`                                                                                                                                                                                |
| `src/lib/puzzles.ts`               | 問題の読み込み（実行時に `fs` で読む）。`Puzzle`（非公開項目を含む）と `PublicPuzzle`（`id` / `title` / `problem` だけ）を型で分けている                                                                                                                   |
| `src/app/api/ask/route.ts`         | 今は `POST { puzzleId, question }` → `{ verdict, confidence }`（`important` は D2 で削除済み）                                                                                                                                                             |
| `src/app/api/solve/route.ts`       | 今は `POST { puzzleId, answer }` → `{ solved, matched, total, truth? }`。`truth` は正解のときだけ返す                                                                                                                                                      |
| `src/app/api/puzzles/route.ts`     | `GET` → `PublicPuzzle[]`                                                                                                                                                                                                                                   |
| `data/puzzles/*.json`              | 問題（`id, number, title, problem, truth, facts[], keyPoints[]`）。`number` は一覧の固定の番号（D9）                                                                                                                                                       |
| `eval/cases/*.json`、`eval/run.ts` | 評価ケースと評価スクリプト                                                                                                                                                                                                                                 |

この節以降は、変更後の設計を書く。

### 4.2 質問判定のリクエスト（1 質問あたり 1 リクエスト）

- **モデル**：`jev-1.13.0` に固定する（R4）。変えるときは、評価をやり直す。
- **state**：`{ problem, truth, facts, playerQuestion }`。
  - `keyPoints` や他の問題は入れない。関係のない情報が増えると精度が落ちる（コンテキストロット）ため。
- **並列に評価する問い**：
  - `answer`（Choice）：「事実である／事実でない／判断できない・無関係」の 3 択。
  - `isValidQuestion`（boolean）：「YES/NO で答えられる形の質問である。内容が物語に関係あるかは問わない」。この確率を**有効確率**と呼ぶ。
  - PoC で聞いていた `importance`（真相の核心に関わるか）は外した（D2）。

### 4.3 合成ルール（`judgeQuestion`）

上から順に判定し、**内部の判定**を決める。

| 順  | 条件                                      | 内部の判定   | 画面の表示         |
| --- | ----------------------------------------- | ------------ | ------------------ |
| 1   | 有効確率 < **0.3**                        | `invalid`    | 言い直してください |
| 2   | `answer` の確信度がない、または < **0.5** | `uncertain`  | どちらともいえない |
| 3   | 「判断できない・無関係」を選んだ          | `irrelevant` | どちらともいえない |
| 4   | 「事実である」を選んだ                    | `yes`        | YES                |
| 5   | 「事実でない」を選んだ                    | `no`         | NO                 |

- **閾値は定数にする**：有効確率 0.3 と確信度 0.5 を、`DEFAULT_JUDGE_OPTIONS` の定数として持つ。
  - 環境変数 `JUDGE_CONFIDENCE_THRESHOLD` による上書きは削除する（R4）。
  - 評価スクリプトも同じ定数を使う。
- **確信度がないとき**：今は確信度 1 とみなしている（`answer.confidence ?? 1`）。これを `uncertain` に変える（R4）。
- **内部の判定の扱い**：`irrelevant` と `uncertain` の区別はサーバー側だけで持ち、API では両方を `unknown` として返す（Q3、§5.2）。

閾値 0.3 の根拠（PoC 3 回目の実測値）：

| 条件     | 普通の質問の最小値 | 質問でない入力の最大値 |
| -------- | ------------------ | ---------------------- |
| baseline | 0.42               | 0.22                   |
| no-facts | 0.60               | 0.22                   |
| en       | 0.55               | 0.11                   |
| yesno    | 0.47               | 0.25                   |

- 閾値 0.3 との差は、下側（質問でない入力の最大値）で最小 0.05、上側（普通の質問の最小値）で 0.12 しかない。値は実行ごとに揺れる。
- 閾値は変えずに凍結し、公開前の評価（確認用データ）で余裕が足りるかを確かめる（Q4、§7）。

### 4.4 正解判定（`judgeSolution`）

- **state**：`{ problem, truth, playerAnswer }`。
- **並列に評価する問い**：
  - 要点ごとに boolean の問い「回答はこの要点を含んでいる」（今は 1 問 3 つ）。
  - **追加する問い**（R3）：boolean の問い「回答は、真相と矛盾する内容や、互いに相反する複数の仮説を含まない」。
- **正解の条件**：すべての要点が 0.7 以上、**かつ**追加の問いが 0.8 以上。
  - 追加の問いの閾値 0.8 は、調整用の評価セット（dev）で決めた（D4）。確認用の評価（holdout）の前に凍結する（§7.2）。
- **当たった要点の数（`matched`）**：追加の問いの結果に関係なく、要点ごとの判定で数える。

## 5. サーバー側の設計（フェーズ 1）

### 5.1 変更点

1. **問題データは fs で読む今の方式のまま**（R1）
   - 今のビルドで、問題データはサーバー関数のファイルトレースに含まれていることを確認済み（レビューで確認）。
   - Vercel の Preview で、実際に読めることを確かめる。
   - 将来 Cloudflare Workers に移す場合（§7.4）は、この方式がそのまま動くかを検証する必要がある。
     - Workers には読み取り専用の仮想ファイルシステム（`/bundle`）があるが、OpenNext 経由で `data/puzzles` を読めるかは未検証。
     - 読めなければ、静的 import に `import "server-only"` を組み合わせる方式に切り替える。そうしないと、クライアントのバンドルに真相が入る経路ができる。
2. **「真相を見る」用の API を追加する**：`POST /api/reveal { puzzleId }` → `{ truth }`。
3. **エラー処理**（R6）
   - `/api/ask`、`/api/solve`、`/api/reveal` を try/catch で包む。
   - 429・529・タイムアウト・通信エラー → `503 { error: "混み合っています。少し待ってからもう一度送ってください" }`
   - それ以外（鍵の誤り、401、400、応答の形の不一致など）→ `500 { error: "判定に失敗しました" }`。原因はサーバーログに残し、クライアントには返さない。
   - Jev への通信に 5 秒のタイムアウト（`AbortSignal.timeout`）を入れる。
   - 429・529 の再試行は、合計時間に上限（例：3 秒）を設ける。上限を超えたら 503 を返す。
4. **`/api/ask` の応答は `{ verdict }` だけにする**（R2、Q3）
   - `verdict` は `"yes" | "no" | "unknown" | "invalid"` のどれか。
   - 確信度・有効確率・`irrelevant` と `uncertain` の区別は返さない。
5. **Jev の経路とモデル**（Q6、R4）
   - 経路は環境変数 `JEV_PROVIDER` で明示する（`direct` / `gateway`）。鍵の有無で自動に選ぶのをやめる。
   - 既定は `direct`（`TYPESAFE_API_KEY` を使う）。
   - `gateway` などの別の経路は切り替え先として残す。ただし本番で使う前に、その経路で評価を回すことを条件にする。
   - モデルは `jev-1.13.0` に固定する。
6. **テスト**（vitest）
   - `judge.test.ts`：偽の `JevClient` を使って、次を確かめる。
     - §4.3 の合成ルール（`uncertain` と `irrelevant` の区別、確信度がないとき）
     - §4.4 の正解の条件（追加の問いが低ければ不正解）
     - state に `facts` が入り、`keyPoints` は入らないこと
   - 各 route のテスト：
     - 入力チェック（400 / 404）
     - 503 と 500 の使い分け
     - `/api/ask` の応答が `{ verdict }` だけであること
     - `/api/solve` の不正解時の応答に `truth` がないこと
7. **問題データの検証**：`npm run check:puzzles` で次を確かめる。
   - 必須項目がそろっている。
   - id とファイル名が一致する。
   - 問題ごとに評価ケースがある。
8. **細かい修正**
   - `judge.ts` の閾値のコメントを PoC 3 回目の値に直す。
   - README を更新する。
   - 入力の文字数は、`trim()` した後で数える。

### 5.2 API の一覧（MVP）

| メソッド・パス     | 入力                                                         | 出力                                             | 真相に関わる情報                             |
| ------------------ | ------------------------------------------------------------ | ------------------------------------------------ | -------------------------------------------- |
| `GET /api/puzzles` | なし                                                         | `PublicPuzzle[]`                                 | 含まない                                     |
| `POST /api/ask`    | `puzzleId`, `question`（200 文字まで）                       | `verdict`                                        | 含まない                                     |
| `POST /api/solve`  | `puzzleId`, `answer`（500 文字まで）                         | `solved`, `matched`, `total`, 正解時のみ `truth` | 当たった要点の**数**（要点の中身は返さない） |
| `POST /api/reveal` | `puzzleId`                                                   | `truth`                                          | 真相そのもの（「真相を見る」を押したとき）   |

| `GET /api/likes`   | なし                                                         | `counts`（問題 ID → いいねの数）                 | 含まない                                     |
| `POST /api/likes`  | `puzzleId`, `liked`（押したら `true`、取り消したら `false`） | `count`                                          | 含まない                                     |

### 5.3 真相を守る方針

**方針（Q1）**：真相を隠すのは、**普通に遊ぶプレイヤーが、うっかりネタバレしないため**。開発者ツールや API を使ってでも答えを知ろうとする人からは守らない。

- `/api/reveal` は誰でも呼べる。真相は機密情報ではなく、ずるをしても損をするのは本人だけなので、許容する。
- `/api/hint` も誰でも呼べ、順番を飛ばして後のヒントを取ることもできる。同じ理由で許容する（D11）。
- `matched` を使えば、どの要点に当たったかを総当たりで探れる。これも同じ理由で許容する。

**それでも守ること**：普通に遊んでいて、真相やヒントが見えてしまう事故を防ぐ。

- `Puzzle` と `PublicPuzzle` を型で分ける。クライアントに返す値は `toPublic()` を通す。
- 問題文は、サーバーコンポーネントから `PublicPuzzle` だけを渡す。`Puzzle` をクライアントコンポーネントに渡さない。
- 真相を画面に出すのは、正解したときと「真相を見る」を押したときだけにする。
- ヒントの本文は `PublicPuzzle` に入れない（渡すのは個数の `hintCount` だけ）。画面に出すのは、確認のうえ開いたものだけにする（D11）。
- `/api/ask` の応答は `verdict` だけにする。確信度や内部の判定の区別がヒントになるのを防ぐ（R2）。
- Jev はテキストを生成しないので、判定の応答に真相の文章が混ざることはない。

## 6. プレイ画面の設計（フェーズ 2）

### 6.1 画面

スタイリングは Tailwind CSS v4 で行い、コンポーネントライブラリは使わない。

- **設定**：`tailwindcss` と `@tailwindcss/postcss` を追加し、`postcss.config.mjs` と `src/app/globals.css` の `@import "tailwindcss";` で読み込む。
- **見た目**：§6.4 の UI デザイン（ベルベットのワインレッドと金）に従う。色・書体は `@theme` のトークンとして定義する。
- **テーマは 1 つだけ**：暗いワインレッドの見た目で固定する。ライトモードは作らず、`dark:` バリアントも使わない。
- **スマホ幅**（約 400px）でも使えるようにする。

**`/`（問題一覧）**

- `listPublicPuzzles()` を使うサーバーコンポーネント。
- 問題ごとに進行状況（未挑戦／挑戦中（質問数）／正解済み／真相を確認済み）を表示する。
  - 進行状況は localStorage から読むので、この表示部分はクライアントコンポーネントにする。
  - サーバーでの描画とブラウザでの描画が食い違わないよう、`useSyncExternalStore` で読む。
- 問題ごとにいいねの数を表示する（D8）。数はブラウザから `GET /api/likes` で取り、自分が押した問題はハートを塗る。取れなかったときは何も出さない。
- 並び順を「新しい順」（`number` の降順）と「いいねの多い順」から選べる（D9）。No. は `number` を出し、並び替えても変わらない。
  - 並び順といいねの数はブラウザにあるので、一覧の部分（`PuzzleList.tsx`）はクライアントコンポーネントにする。渡すのは `PublicPuzzle` だけ。
  - サーバーでの描画は新しい順で、保存した並び順があれば hydration の後に切り替わる。
- 問題一覧のページ下部の注意書きの下に、Google アナリティクスを使っていることの明記と、Google のポリシーへのリンクを置く（D10）。
- ページ下部の注意書きの下に、GitHub のリポジトリへのリンクを GitHub のアイコンで置く（別タブで開く）。アイコンの色は GitHub のブランドガイドラインに従い、白で固定する（ホバーでも変えない）。

**`/puzzles/[id]`（プレイ画面）**

- 問題文はサーバーで取得し、`PublicPuzzle` として渡す。
- **質問ログ**：質問と判定を時系列で並べる。判定は囲みのない文字だけで表示する（YES／NO／どちらともいえない／言い直してください。§6.4）。表示の仕方は `VerdictLabel.tsx` にまとめる。
- **入力欄**：200 文字まで。Enter で送信する。送信中は二重送信を防ぐ。503・500 のときは、入力を消さずにエラーを表示する。
- **回答パネル**：
  - 不正解なら「{total} つの要点のうち {matched} つ」と表示する。要点の数は固定にしない（Q2）。
  - 正解なら真相を表示する。
- **「真相を見る」ボタン**：確認のうえ `/api/reveal` を呼び、真相を表示する。確認の文言で、真相を見るとその問題が終わることを伝える（例：「真相を見ると、この問題は終了します。よろしいですか？」）。ボタンの文言は「降参して」を付けない（UI デザインの検討で決定）。
- **ヒント**（D11）：問題文の下に置く。「ヒント n を見る」を押すと、確認のうえ `/api/hint` で次のヒントを取り、開いた順に並べる。すべて開くとボタンを消す。
- **やり直すボタン**：その問題の進行状況を消して、最初から遊べるようにする。
- **いいねボタン**（D8）：真相の表示に置き、今の数を一緒に出す。押すと数を先に変え、保存に失敗したら元に戻す。もう一度押すと取り消せる。
- **遊び方**：初回だけ表示する。次の内容を含める。
  - YES/NO で答えられる質問をすること。
  - 「〜ではないのですか？」は答えがぶれやすいので、肯定形で聞くこと（Q7）。
- **注意書き**：「質問は判定のため外部の AI サービスに送られます。個人情報は入力しないでください」（§7.4）。

### 6.2 進行状況の保存

- `src/lib/progress.ts` に読み書きをまとめる。
  - キー：`soup-of-jev:v1:progress:<puzzleId>`（問題データを変えたときに古い記録を捨てられるよう、バージョンを入れる）
  - 値：`{ log: { question, verdict }[], status: "playing" | "solved" | "gave-up", truth?: string, hints?: string[] }`
  - `hints` は、開いたヒントの本文を開いた順に保存する（D11）。やり直すと消える。任意の項目なので、キーのバージョンは上げない。
  - `truth` は、正解したときか「真相を見る」で表示したときに保存する。開き直したときは、それを表示する。
  - 遊び方を表示したかどうかは、`soup-of-jev:v1:seen-howto` に保存する。
  - いいねを押したかどうかは、`soup-of-jev:v1:liked:<puzzleId>` に保存する（D8）。やり直しても消さない。
  - 問題一覧の並び順は、`soup-of-jev:v1:list-sort` に保存する（D9。`newest` か `likes`）。
- 質問数には、`invalid`（言い直してください）も含めて数える。
- 読み書きはすべて try/catch で包み、保存できない環境（シークレットウィンドウなど）でも遊べるようにする。
- 端末をまたいだ引き継ぎはできない。MVP では許容する。

- **主ボタン**：金の塗り、暗い文字（`#2A0710`）、`#ECD392` の 1px の枠線。高さ 44px 以上。
- **副ボタン**：透明の地、金 60% の枠線、金の文字。
- **入力欄**：地は `#24060D`、枠は金、文字は象牙。高さ 48px。
- **進行状況の表示**（問題一覧）：挑戦中は金の枠線、正解済みは金の塗り＋チェック、未挑戦は点線の枠。判定ではなく状態の表示なので、囲みを残している。

#### 文言

- 質問の送信ボタン：「**問う**」
- 真相を表示するボタン：「**真相を見る**」（「降参して」は付けない）
- 問題番号：「No. 1」のように通常の数字（ローマ数字にしない）
- 欧文のラベル：THE MYSTERY（問題文）、QUESTIONS（質問ログ）、YOUR ANSWER（回答欄）、SOLVED（真相の表示）

## 7. 評価の拡充と公開（フェーズ 3・4）

PoC の「条件付き」の条件（評価セットが小さい、合わせ込みの可能性）を解消するフェーズ。

### 7.1 評価セットを作り直す

- **問題を増やす**：3 問から 8 問程度にする。有名でない問題、真相が長い問題、ひねりの多い問題を含める。
  - 各問に `facts` と `keyPoints` を付ける。
- **質問判定のケース**：1 問あたり約 40 件。PoC と同じカテゴリ構成にする。
  - カテゴリ：直接、推論、素直な否定、確認型、両方に読める否定、無関係、質問でない入力、インジェクション
  - **質問でない入力を増やす**（1 問あたり 3 件 → 8 件程度）。件数が少ないと「すり抜け 0 件」の根拠が弱いため（R5）。
  - 複合質問（「A で、かつ B ですか？」）と、長い質問も加える。
- **正解判定のケース**：1 問あたり 4 件 → 8 件程度に増やす。
  - 正解、言い換えた正解
  - 部分正解（`matched` の正確さを確かめるため。Q2）
  - 誤答
  - **仮説を並べた回答**、**正解に誤りが混ざった回答**（R3）
- **期待値のレビュー**：作成者（Claude）とは別に、**ユーザー自身**がレビューする（Q8）。
  - 負担を減らすため、事前に別のエージェントに怪しいケースを洗い出させ、その候補を中心に見てもらってもよい。

### 7.2 評価の進め方（R5）

1. **調整用（dev）と確認用（holdout）に分ける**：問題単位で分ける（例：dev 4 問、holdout 4 問）。
2. **dev で決めてから凍結する**：dev で次を決め、凍結する。凍結した後は変えない。
   - 正解判定の追加の問いの閾値
   - 問いの文言
   - 有効確率の閾値 0.3 と確信度の閾値 0.5。PoC で決めた値のまま、dev でも問題がないかを見るだけにする（Q4）。
3. **holdout は 1 回だけ評価する**：`--repeat=3` で実行し、§7.3 の基準で判定する。
   - 不合格の場合、閾値などを見直してよい。ただし、その後は**新しい holdout** を用意して評価し直す。同じ holdout で見直しを繰り返すと、合わせ込みになる。
4. **`eval/run.ts` の拡張**
   - `--repeat=N`：同じ条件で N 回実行し、カテゴリごとの正答率の最小値と平均、有効確率の分布の揺れを出す。
   - `--split=dev|holdout`：どちらのセットを評価するかを指定する。
   - 評価結果の JSON に、モデルのバージョン・閾値・経路を記録する。
5. **結果**を `research/poc-results.md` に「公開前評価」として追記する。

### 7.3 公開の判定基準

holdout、baseline 条件、`--repeat=3` の**最小値**で判定する。

| 項目                                                           | 基準                                                     |
| -------------------------------------------------------------- | -------------------------------------------------------- |
| 全体の正答率（両方に読める否定は除く）                         | 95% 以上                                                 |
| 直接                                                           | 95% 以上                                                 |
| 推論                                                           | 85% 以上                                                 |
| 質問でない入力（**参考値**。D6）                               | すり抜け 0 件                                            |
| 有効確率の余裕（**参考値**。D6）                               | 質問でない入力の最大値 ≤ 0.25、普通の質問の最小値 ≥ 0.35 |
| インジェクション                                               | 100%                                                     |
| 正解判定：誤って正解にした件数（仮説の羅列・誤りの混入を含む） | 0 件                                                     |
| 正解判定：正しい回答を正解にできた割合                         | 90% 以上                                                 |
| 部分正解の `matched` の正確さ                                  | 90% 以上                                                 |

- **参考値の項目**（D6）：件数と値は報告するが、合否には使わない。すり抜けは YES/NO を返すだけで、取りこぼしは言い直しを促すだけなので、どちらも誤った答えにはならないため。
- 両方に読める否定疑問文は、YES/NO のどちらでも正解としているため、正答率が上がる方向に偏る。全体の正答率からは除き、別に件数だけを報告する。
- 基準を満たさない場合は、§7.2-3 の手順で見直すか、LLM へのエスカレーションの計画を別に立てる。

### 7.4 公開（フェーズ 4）

- **公開先：Vercel Hobby（無料プラン）**（D1）
  - 前提：個人・非商用（Hobby の利用条件）。公開先の利用料は月 $5 程度まで。
  - 選んだ理由（2026-09-22 時点の公式ドキュメントで確認）
    - 費用が $0 で、上限を超えても請求は発生しない（該当する機能が一時停止する）。費用の心配を、Jev 側だけに絞れる。
    - Next.js がそのまま動き、コードの変更が要らない。R1 の決定（fs 方式）がそのまま使える。
    - WAF のレート制限ルールを 1 つ使える（無料枠は月 100 万リクエスト）。Q9 の①を満たせる。
  - Hobby の主な制限
    - 関数の呼び出しは月 100 万回まで。CPU は月 4 時間まで。
    - WAF のレート制限ルールは 1 つまで。カスタムルールは合計 3 つまで。
    - 実行時ログは 1 時間分しか残らない。R6 のサーバーログも同じ。
    - Spend Management（支出管理）は使えない。ただし無料プランなので、Vercel 側の超過請求はない。
  - Jev を直接 API で呼ぶので、Vercel の AI Gateway は使わない。
- **Cloudflare Workers を検討し直す条件**
  - 商用化するとき：Vercel は有料プラン（1 人あたり月 $20）が必要になり、予算を超える。Cloudflare Workers の有料プラン（月 $5）が有力になる。
  - Workers AI 経由の Jev（`typesafe/jev`、`jev-1.13.0`）が、料金や運用の面で有利だとわかったとき。料金は未公開で、使う場合はその経路で評価を回す（§5.1-5）。
  - 移す場合に必要なこと：
    - Next.js を動かすアダプター（`@opennextjs/cloudflare`）
    - 問題データの読み込み方の検証（§5.1-1）
    - 有料プランへの加入。無料プランは 1 リクエストあたり CPU 10ms までで、ページのサーバー描画が収まらないおそれがある（未検証）。
  - 移しやすくするため、MVP の実装では Vercel 固有の機能に依存しない。Jev の呼び出しは `JevClient` の裏に閉じ込める。
- **環境変数**：`TYPESAFE_API_KEY`、`JEV_PROVIDER=direct`。アクセス解析（D10）に `NEXT_PUBLIC_GA_MEASUREMENT_ID`（Production のみ）。いいねの保存先（D8）に `KV_REST_API_URL`、`KV_REST_API_TOKEN`（Marketplace で Upstash Redis を追加すると入る。`UPSTASH_REDIS_REST_URL`／`_TOKEN` でもよい）。
- **費用と濫用の対策**（Q9）
  - 最悪の場合（Jev のレート制限 1,200 リクエスト/分をすべて使われた場合）、費用は 1 日約 $690 になる。
  - ① Vercel WAF のレート制限ルールで、IP ごとに `/api/*` を制限する（例：60 秒の窓で 60 リクエスト）。
    - Hobby で使えるルールは 1 つなので、`/api/*` にまとめてかける。
    - カウンターは地域ごとに数えられる。複数の地域から来ると、設定値を超えて通ることがある。
  - ② TypeSafe 側で、支出の上限かアラートを設定する。公開時（2026-09-23）に確かめたところ、**設定できなかった**。請求額を定期的に確かめる運用で補う（D7）。
- **データの扱い**
  - プレイヤーの質問文は、TypeSafe（米国ホスト）に送られる。
  - ゼロデータ保持（ZDR）はエンタープライズ階層のみで、それ以外の保持期間は公表されていない。
  - こちらのサービスでは質問を記録しない（Q5）。画面に注意書きを置く（§6.1）。
  - アクセス解析（Google Analytics 4、D10）には、問題 ID・判定・数だけを送り、質問文・回答文は送らない。
- **公開の手順**：Preview デプロイで通しプレイを確認してから、本番に昇格する。
  - 実際には、Vercel の最初のデプロイは本番の URL に出るため、URL を知らせる前にその URL で通しプレイを確認した（D7）。
